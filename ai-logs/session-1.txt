  Traps in the levels you can run:
  - Order: sort inbound messages by occurred_at, then message_id. That's the
    order Pigeon's truth uses, not arrival order.
  - Duplicates: dedupe on a unique (workspace, message_id) index. Never dedupe
    on event id, because a status event and an inbound event are different
    events.
  - Status regressions: delivered can arrive before sent. Rank the statuses and
    never move backwards. Key statuses by client_ref, because the status webhook
    can arrive before the slow 12 s HTTP response gives you the pm_ id.
  - Never send twice: always send Idempotency-Key = client_ref. Give up on
    Pigeon after about 3 s and retry with the same key. Pigeon replays the
    original response instead of sending again.
  - Retry-After: the rate limit and the 2 s cool-off must live in Redis, shared
    by every copy (level 3). During the outage, back off; more than 6 requests a
    second loses points. Cap the backoff at a few seconds so sends recover
    quickly afterwards.
  - Claim race: upsert the conversation first (ignoring duplicate-key errors),
    then do one conditional update: findOneAndUpdate({assignee: null or me}).
  - Login across copies: the load balancer can send /auth/callback to a
    different copy than /auth/login. The PKCE verifier, state and sessions must
    live in Redis or a cookie, not in memory.
  - WebSocket seq order: if two copies each run INCR and then publish, frames
    can arrive as 6 then 5, and the check marks that "NOT increasing". Use one
    Lua script that does INCR and XADD to a Redis Stream per workspace in the
    same step. Each copy then reads with XREAD and fans out, and replay is just
    an XRANGE after seq.
  - Reset: use deleteMany, not drop. Dropping a collection loses its unique
    indexes mid-run. Keep the session keys.
  - Start-up: /healthz should answer 200 only once Mongo, Redis and the indexes
    are ready. Read PORT from the environment.

● Answer to your question first, then I'll build step 0.

  Why a Mongo conditional update and not Redis SET NX:
  - The claim is the source of truth that the snapshot, the API and the
    WebSocket all show. It must be as durable as the conversation it sits on, so
    it belongs in the same document and the same atomic write.
  - A Redis lock is a second system. "Take the lock, then write the assignee to
    Mongo" is two steps, and a crash between them leaves a lock with no assignee
    or an assignee with no lock.
  - A conditional findOneAndUpdate is one atomic operation: {contact, assignee ∈
    {null, me}} → $set assignee. The holder claiming again matches the filter,
    so it gets 200 with no special case.

  If Redis restarts:
  - Claims are unaffected, because they live in Mongo.
  - Rate-limit bucket and cool-off are lost. The bucket would restart full (8
    tokens) and a 2 s Retry-After would be forgotten. The worst case is one
    burst of early requests, which Pigeon would answer with a 429 and a new
    cool-off. I'll treat a Redis outage as "back off 2 s and retry". The outbox
    in Mongo means no reply is lost.
  - Sessions are lost, so users have to log in again. I'll note that in
    DECISIONS.md.
  - The event stream and seq counter are lost. That is the real problem, because
    seq would restart at 0 and break after= replay. I'll keep the seq counter
    in Mongo, or re-seed it from the highest stored seq, so it never goes
    backwards.

  What I chose

  - Idempotency-Key: sb-<client_ref>. It depends only on the reply, never on the
    attempt, the copy or the time. Every retry from any copy, before or after a
    crash, sends the same key, so Pigeon returns its original answer instead of
    sending again.
  - Attempt timeout: 3 s. Pigeon's slow path answers after 12 s, so we always
    time out on it and retry with the same key. The retry gets an instant
    replay.
  - Lease: 10 s.
    - It has to outlast one attempt (3 s) with margin, so a healthy copy never
      loses its row mid-send.
    - It also has to be short enough that a dead copy's rows are retaken well
      inside the 60 s limit.
    - The measured cost is that after a kill -9, a row that was in flight waits
      up to 10 s. Both level 2 and level 3 recovered inside that.
  - Backoff: 0.5 s, 1 s, 2 s, 4 s, then 5 s, with ±20% jitter and a hard cap.
    During the 8 s outage the check counted 25–26 requests, against a penalty
    threshold of 48.
  - Rate limit: a bucket of 7 refilling at 3.5 per second per workspace, just
    under Pigeon's 8 and 4. It sits in Redis and one Lua script does the whole
    step, so copies can't both spend the last token. A 429 sets a shared
    cool-off in Redis for the Retry-After plus 250 ms. It is never triggered in
    practice, because the bucket keeps us below Pigeon's limit.

  Your two cases

  - Dying after the 202, before Pigeon is called: the row is already in Mongo
    and still pending, so any copy sends it. A copy that dies after claiming the
    row but before sending has its row retaken only once the lease expires.
    These are tests case 1a and case 1b.
  - Pigeon accepts, but answers after our timeout and after the lease:
    - The retry carries the same key, so Pigeon replays its answer and nothing
      is sent twice (case 2a, a real HTTP server with the real client).
    - If the stale answer finally arrives after another copy finished, nothing
      doubles or reverts (case 2b).
    - If a stale failure arrives, it can't overwrite the copy that now holds the
      row, because writes that give a row up are checked against a per-claim
      token (case 2c).
    - Success is the one write I deliberately don't check against the lease,
      because Pigeon gives both copies the same answer.

  Weak spots to know about

  - Clock: lease times use each server's clock. All copies share one machine
    here, so that's fine, but across machines clock skew would matter.
  - Redis down: the worker sends nothing, because it can't see the rate limit.
    Replies stay safe in Mongo and go out when Redis returns.
  - Permanent failure: a 400 from Pigeon marks the reply dead and failed and
    stops. A 401 (wrong API key) keeps retrying at the 5 s cap, in case someone
    fixes the key.
